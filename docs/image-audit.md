# Аудит кінцевого образу

```bash
make audit-image
```

Потрібні Docker, uv і доступ до мережі. Команда збирає кінцевий Distroless-образ
із поточного checkout, експортує його за незмінним image ID і перевіряє через
Trivy 0.76.2, закріплений за SHA-256. Застосунок і MongoDB запускати не потрібно.
Trivy працює в окремому контейнері, без доступу до Docker socket.

Для стороннього або вже зібраного образу використовуйте порожню політику:

```bash
mkdir -p artifacts
printf '{"schema_version":1,"exceptions":[]}\n' > artifacts/no-image-exceptions.json
uv run --locked python -m scripts.audit_image --image goit-cs-hw-06-app \
  --exceptions artifacts/no-image-exceptions.json
```

Кожен запуск створює нову папку `artifacts/image-audit/<час-UTC>/`:

- `report.md` — підсумок, image ID, платформа, час, CVE та винятки;
- `report.json` — ті самі дані для автоматизації, версія Trivy й бази CVE,
  Git checkout та SHA-256 файлів;
- `trivy.json` — повний результат, включно з невиправленими вразливостями;
- `sbom.cdx.json` — CycloneDX: системні пакети й Python-залежності образу;
- `exceptions.json` — копія застосованої політики.
- `exception-review.json` — SHA-256 перевірених джерел і перевірка передумов
  винятків у зібраному образі, якщо політика містить винятки.

SBOM створюється з того самого результату Trivy, без повторного сканування.
Скрипт звіряє image ID та наявність усіх знайдених пакетів у SBOM, навіть без CVE.
Image ID — digest конфігурації локального образу; registry digest записується
окремо, якщо він є. Для `--image` Git checkout не видається за джерело збірки.
Тимчасовий tar видаляється після перевірки, база Trivy кешується в `.cache/trivy/`.
Звіти й кеш не входять до Git. `--output <нова-папка>` задає власний шлях;
наявний звіт не перезаписується.

## Коли перевірка падає

Скрипт повертає `0` для PASS, `1` для знахідок або порушень політики,
`2` для помилки збірки, сканера чи неповного результату. Make передає помилку
як власний ненульовий код. Report і SBOM зберігаються навіть при FAIL.
При ERROR частина файлів може бути відсутня; такий запуск не є успішним аудитом.

Блокуються CRITICAL, HIGH і UNKNOWN без чинного винятку, незалежно від наявності
виправлення. UNKNOWN потребує оцінки, а не автоматичного визнання безпечним.
MEDIUM і LOW залишаються у звіті. Прострочена база CVE, непідтримувана ОС,
порожній список пакетів або ОС після завершення підтримки теж не дають PASS.

Аудит виконується окремо від `make check`, як Python/npm audit: він потребує
мережі, а результат змінюється разом із базою CVE навіть без змін коду.

## Винятки

Політика — у `security/image-exceptions.json`.
Відсутність виправлення сама по собі не є причиною приховувати CVE.

Виняток додається після перевірки advisory та того, як код використовує пакет.
Потрібні точні `type`, `package`, `version`, `vulnerability`, а також `reason`,
`owner`, `expires` у форматі `YYYY-MM-DD` і HTTPS-посилання `reference`
на advisory або розбір. Поля для зіставлення беруться з `report.json`.
У `reason` варто записати, чому вразливий шлях недоступний або які обмеження
зменшують ризик, і що потрібно для остаточного виправлення.

Виняток діє до кінця вказаного дня UTC і потрапляє в report разом із причиною.
Він не видаляє CVE з сирого результату. Wildcard і дублікати заборонені;
прострочений або вже непотрібний виняток робить перевірку неуспішною.
Після оновлення пакета виняток для старої версії не застосовується.

Розбір від 05.11.2026 стосується лише нашого сервера. Його передумови:

| Компонент | Чому вразливий шлях недоступний |
| --- | --- |
| Expat і Python XML | Сервер приймає форму/JSON, працює з BSON і не розбирає XML. |
| Python HTMLParser | Віддаємо готовий HTML; HTMLParser не обробляє введені дані. |
| Python TLS | Немає TLS-сервера, SNI callback або wrap_bio; PyMongo використовує звичайний TCP. |
| Python tarfile | Застосунок не розпаковує архіви; backup-скрипт не входить до образу. |
| Python getaddrinfo | Host проходить allowlist, port — перевірку цілого числа; NUL із .env відхиляється до MongoClient. |
| SQLite | Сховище — MongoDB; немає SQLite, SQL або завантаження SQLite/WAL-файлів. |
| ncurses, util-linux | CVE стосуються infocmp, mount і nsenter. Цих програм у Distroless немає. |
| zlib | CVE стосується gz* запису після помилки; Python zlib використовує deflate/inflate. Mongo compression не ввімкнено. |

Це оцінка застосовності до поточної програми, а не виправлення самих бібліотек.
Окремі CVE, точні версії, причини й джерела наведені в JSON-політиці.
Винятки діють до **05.12.2026 включно**; після цього аудит знову падає.
Не додавайте TLS, XML, SQLite чи обробку архівів без нового розбору.

`security/image-exceptions.review.json` фіксує SHA-256 main.py, Dockerfile,
Compose, Python lockfile та решти вхідних файлів runtime. Зміна будь-якого з них
блокує застосування винятків до нового розбору. Аудит додатково запускає коротку
перевірку образу без мережі та запису на диск: UID 65532, hash main.py,
відсутність infocmp/mount/nsenter. Ця перевірка підтверджує передумови ручного
розбору, але не доводить недосяжність усіх шляхів автоматично.
Для `--image` ці винятки заборонені: сам збіг версій пакетів не підтверджує,
що чужий образ містить саме наш застосунок. Для іншої `--exceptions` політики
супровідний файл має ту саму назву з суфіксом `.review.json`.

## Що перевірено локально

05.11.2026, Linux ARM64, image ID
`sha256:fc1a202ddea9082efe71f1afdff638e0be0f6d020ce4597a9fe1545ac9b1db07`:
38 Debian-пакетів і 3 Python-залежності, усі включено в SBOM.
Знайдено 31 HIGH, 107 MEDIUM, 54 LOW і 11 UNKNOWN; CRITICAL немає.
Це кількість пар CVE/пакет: одна CVE може стосуватися кількох пакетів Python.
У Python-залежностях знахідок немає. Для системних знахідок база на момент
перевірки не вказувала виправлених версій. Оновлення Distroless принесло нову
tzdata, але не усунуло ці CVE. Результат — **PASS із 42 точними винятками для
23 CVE**, нуль блокувань. Сирий звіт зберігає всі 203 знахідки.

Цей SBOM описує один кінцевий образ app і одну платформу. MongoDB, інші
архітектури та build stages не охоплені. Зібраний JavaScript не містить повного
npm dependency graph, тому `make audit` і `make audit-frontend` залишаються потрібними.
SBOM — перелік знайдених компонентів, не доказ відсутності всіх вразливостей.
Lockfile SBOM, перевірка Swagger UI та загальний `make audit-all` описані
в [dependency-audit.md](dependency-audit.md).

Використано [Trivy image scanning](https://trivy.dev/docs/latest/target/container_image/)
і [CycloneDX export](https://trivy.dev/docs/latest/supply-chain/sbom/).
Це локальний файл, без підпису чи registry attestation.
[Docker BuildKit SBOM attestations](https://docs.docker.com/build/metadata/attestations/sbom/)
можна додати при публікації образів; для цього локального аудиту вони не потрібні.
