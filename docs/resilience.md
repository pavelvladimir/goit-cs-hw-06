# Збої, навантаження та резервні копії

## Що відбувається при збоях

HTTP і TCP обмежують кількість одночасних обробників. При перевантаженні HTTP
повертає 503 із `Retry-After: 1`, а TCP закриває зайве з'єднання.
`RECEIVE_TIMEOUT` діє на весь запит: повільне надсилання байтів не поновлює відлік.

Якщо MongoDB записала повідомлення, але відповідь загубилася, клієнт не може
знати результат. Тому повторних POST автоматично немає. Інтеграційний тест
навмисно відкидає TCP-підтвердження і перевіряє, що при HTTP 503 у БД є лише один запис.

```bash
make test-resilience
```

Це перевіряє перевантаження, втрату підтвердження, резервні копії та блокування
паралельних backup/restore у власному тестовому Compose-проєкті.

## Навантаження

```bash
make test-write-load
make test-write-load WRITE_LOAD_SECONDS=30
```

Тест надсилає справжні POST при паралельності 1, 8 і 16. Кожна фаза триває
10 секунд за замовчуванням; можна задати 1–60. Worker чекає відповідь і починає
не більше 20 запитів/с. Це задане навантаження, а не пошук максимальної місткості сервера.

Кожна спроба має унікальне повідомлення. Після тесту відповіді звіряються з MongoDB:
підтверджений запис має існувати рівно один раз. Для 503 і мережевих помилок окремо
рахуються знайдені та відсутні на момент перевірки документи. Окремо перевіряється
ще один запис після навантаження.

`artifacts/write-load-report.json` містить швидкість записів, статуси, p50/p95/max
і вибірки RAM та кількості потоків. Ресурси читаються приблизно кожні 0,5 секунди
плюс час запуску спостерігача. Це пам'ять app разом зі спостерігачем, без MongoDB;
максимум вибірок не є точним піком. Дані й volume цього тесту прибираються автоматично.

## Резервні копії

```bash
make backup BACKUP_DIR=backups/before-upgrade
make restore BACKUP_DIR=backups/before-upgrade RESTORE_DATABASE=restore_check
```

Backup тимчасово зупиняє app і виконує `mongodump`. Наприкінці скрипт намагається
повернути попередній стан app, також при помилці. Готовий backup залишається,
навіть якщо запуск app не вдався. Інших клієнтів, які пишуть у БД, у цей час бути не повинно.
Папка backup має бути новою. У ній зберігаються `archive.bson` і `manifest.json`
з датою та SHA-256; каталог приватний, файли мають права 0600.

Restore перевіряє checksum і створює нову БД із префіксом `restore_`.
Наявну БД він не перезаписує. Архів і manifest мають бути з довіреного джерела.
При невдалому restore може залишитися часткова копія: перед повтором перевірте її
та виберіть іншу назву. Копію backup варто тримати також поза диском із робочою БД.

Backup і restore одного Compose-проєкту не можуть виконуватися одночасно.
Друга команда завершується кодом 1 до виклику Docker. Блокування тримається до
кінця прибирання й відновлення app, незалежно від назви backup або копії репозиторію.

Це локальний `flock` для одного OS-користувача на macOS/Linux. Різні проєкти можуть
працювати паралельно; однакові назви блокуються навіть для різних Docker contexts.
Інші хости, користувачі й ручні команди Docker/MongoDB цим блокуванням не охоплені.
Файли в `/tmp/goit-cs-hw-06-archive-<UID>` залишаються після операції — видаляти їх
для розблокування не потрібно, під час роботи скриптів це робити не можна.

При SIGTERM/SIGKILL локальне блокування звільниться, але cleanup може не завершитися.
Перед повтором перевірте стан app, незавершену копію та відсутність активних
`mongodump`/`mongorestore` у MongoDB-контейнері.
